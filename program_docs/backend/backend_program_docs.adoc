[#sec:technicalDocumentationOfBackend]
= Technická dokumentace backendu

Celá aplikace je rozdělena na samostatný backend a frontend.
Backend je postaven na architektuře mikroslužeb.
Skládá se konkrétně ze dvou služeb, které spolu komunikují pomocí brokera zpráv RabbitMQ 3.8.
První služba je implementována ve frameworku Spring Boot 3.1.0 a poskytuje API pro komunikaci s frontendem (tzn. grafickou částí aplikace).
Druhá služba je implementována v jazyce Python 3.11 a vykonává samotné operace načítání modelů ze souboru a generace scén.

Pro obě vytvořené služby byl vytvořen soubor Dockerfile, aby je bylo možné použít v Dockeru.
V případě Spring Boot služby byl tento soubor nastavený tak, aby se vždy provedla kompilace a nedocházelo tak k situacím, kdy se po provedení změn na kompilaci před jejím spuštěním v Dockeru zapomene.
Vytvořené obrazy Dockeru jsou poté využívány v souboru `docker-compose.dev.yml`, s jehož pomocí lze poté celý backend spustit jediným příkazem (viz <<sec:launchBackend>>).

[#sec:communicationWhileExecutingActions]
=== Popis komunikace při prováděných akcích
Klient se musí nejprve připojit k Socket.IO serveru (zde implementován pomocí knihovny Netty Socket.IO).
Po tomto připojení je mu posláno UUID, které později slouží jako autentizace při veškerých požadavcích na API.
Toto UUID je zároveň uloženo do ConcurrentHashMap ve třídě `ActiveClientsService` (balíček `common.services`).
V rámci struktury do této mapy ukládané jsou uchovávány také informace o jednotlivých operacích, které klient započal.

Při provolání kteréhokoliv endpointu API je vždy v rámci filtru vůči této službě zkontrolováno ID v hlavičce pod hodnotou klíče `client-id`.
Pokud tato hodnota chybí, nebo zde není vedena, je vrácen kód HTTP 401 jako kdyby uživatel nebyl přihlášený.
Pro realizaci tohoto omezení byla použita knihovna Spring Security 6.1.2.

Pokud požadavek proběhl v pořádku, je odeslán pokyn na zahájení operace do fronty a klientovi se vrátí její UUID.
Po dokončení operace se ze zprávy vyextrahují potřebná data a uloží do dočasného souboru pro pozdější zpřístupnění klientovi.
Jakmile klient zažádá o výsledek operace, je obsloužen s pomocí třídy InputStreamResource, které se předá proud k danému souboru.
Pro serializaci dat do formátu JSON je použita knihovna Jackson a každé operaci může příslušet 1 – n souborů s výsledky.

[#sec:processingOfModelParsingOperations]
=== Popis zpracování operací parsování modelů
Jakmile je obdržena zpráva z požadavkem, je z ní získán obsah souboru a vytvořen dočasný soubor, který se předá knihovně assimp-py.
Pomocí této knihovny jsou ze souboru získána data o modelu, která jsou poté převedena do vlastní reprezentace.
Ta je poté převedena do slovníku a následně do řetězce JSON, který se poté v rámci dalšího řetězce JSON odešle do fronty pro odpovědi.
V případě chyb se odešle pouze obalový řetězec JSON s informací o chybě.

[#sec:processingOfSceneGenerationOperations]
=== Popis zpracování operací generace scén
Po obdržení zprávy s požadavkem se z obsahu sestaví místní reprezentace tohoto požadavku, ze kterého se poté sestaví parametry pro generaci a také samotný model a úchopové body.

Na základě těchto parametrů jsou poté generovány náhodné pozice pro objekt.
V případě plně náhodných pozic se kontrolují kolize s pomocí knihovny https://trimsh.org/trimesh.html[trimesh], aby se minimalizovalo prolínání modelů do sebe.
Pro generaci pomocí vzorkování Poissonova disku byla použita knihovna https://pypi.org/project/poisson-disc/[poisson-disc].
V obou případech jsou vygenerované rotace zcela náhodné a způsob generace rotace tak nelze parametrizovat.

Pokud byla zvolena možnost použití simulací, jsou vygenerované pozice použity jako výchozí hodnoty pro fyzikální engine https://pybullet.org/wordpress/[PyBullet], s pomocí kterého je simulace provedena.

Poté jsou pomocí afinních transformací dopočítány nové pozice a rotace úchopových bodů na základě jejich lokálních transformací a nových globálních transformací daného modelu.

Poté je dle rozměrů zájmové oblasti dopočítána pozice kamery a výsledné hodnoty jsou posléze převedeny do slovníku.
Tento slovník je poté převeden do řetězce JSON, zabalen do dalšího řetězce JSON s informacemi o úspěchu operace a odeslán do fronty.
